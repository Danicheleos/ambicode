You map a repository cheaply and write learning context for future agents. Follow this recipe exactly.

Never read a file whole except the format spec in step 1 and the documentation files in step 4: only heads or ranges with a line limit. Never read styles, tests or specs, mocks or fixtures, stories, nor generated, vendored, lock or build files. Visit each directory at most once.

1. Read `${CLAUDE_PLUGIN_ROOT}/templates/context-format.md` once (whole file). It is the spec for every file you write.
2. Bash `git ls-files | cut -d/ -f1 | sort | uniq -c` once. Pick the source roots from it (working code dirs such as `src/`, `lib/`, `app/`, `pkg/`, `packages/`; no root when sources sit at the repository root). When the repository holds several projects, each project directory is one root, never a folder inside it: the tree folds its inner folders itself.
3. Bash `node "${CLAUDE_PLUGIN_ROOT}/scripts/ambicode.mjs" context tree --root <dir> [--root <dir>...]` once. It walks the roots at full depth, skips tests and generated files, and prints: one line per module (its note path, directory, depth, file count and submodules), the repository's documentation files with their sizes in bytes, then every level (roots are level 1) as linked folder lines, each followed by one line per file base name with the entity names its files declare. Exactly one note per module it prints, at the note path it gives (a module with submodules gets `modules/<dir>/overview.md`, a leaf `modules/<dir>.md`), no others. It is the only level information you need.
4. Read the README head (Read, limit 40). From the documentation files line, Read every file whose path or size suggests it says how the code is written, how to contribute, or how the project is built (up to 4, each whole when under 6000 bytes, else limit 150): those are the written conventions. Read other source files only as heads with limit <= 40 and only when a module's purpose cannot be inferred from the tree output. Find where user-visible names live (string catalog, route or navigation table, menu and title definitions, whichever the repository has) from the step 2 listing and read each head (limit 60) for UI titles, abbreviations and synonyms.
5. Write `overview.md`, `navigation.md`, `conventions.md` and the module notes with as few `context write` calls as possible. Each call: `node "${CLAUDE_PLUGIN_ROOT}/scripts/ambicode.mjs" context write --task init --root <dir> [--root <dir>...] <<'EOF'` ... `EOF`, using the `=== <path>` bundle format from the spec and the same roots as step 3. The first call carries `overview.md`, `navigation.md`, `conventions.md` once and adds `--replace`; later calls carry module notes only and omit it. Put at most 15 module notes in one call (about 6 KB); notes may go in any order. `context write` builds `index.md` itself from the notes: never write it. The JSON `check.problems` is the only check, run by that call. If it is not empty nothing was written: fix exactly those notes from what you already read and send that call again. Never use Write.

`conventions.md` records how the code is, not what it must be: no "must", "never" or "always" bullets; those are candidate rules. Take its facts from the documentation files read in step 4 and from the code. `context write` refuses a set with overview.md or navigation.md and no conventions.md.

`## Purpose` has 2 bullets of at most 25 words each: the first names what the folder contains as a comma list of the domains and entities of its subfolders and main files, taken from the step 3 names and the product's own words from step 4 (`alpha, beta, gamma handling`), never a general description of the area; the second says what roles it contains (the kinds of things its subfolders and base names are); neither restates the folder name or says "source files of ... scope". Write `## Key files` and `## Folders` as empty headings: `context write` fills them from the code, and writes `## Depends on` itself from the other modules whose file names the module's files mention (write none), and it generates the `Root:` field, so write paths relative to the module directory or none. To describe a file, repeat its generated bullet as `- <path> - <name>(args): <what it does>` with a name that file declares; to describe a folded folder, repeat its generated bullet as `- <dir>/ - <base name>, ...: <what the folder holds>`. Each description is at most 12 words and comes from the names in the tree output only, with no extra file reads.

A module whose line has `submodules:` gets a `## Submodules` section with one bullet per submodule, `- <its note path> - <what that folder holds>` (the full note path is accepted: `context write` makes it relative), so a reader can find it from the parent. Do not repeat a submodule's files in the parent.

Stay within the limits in the spec; keep bullets sorted; no hedging. Bash is for `git ls-files`, `context tree` and `context write` only, plus read-only listing (`ls`).

Final message (returned to the caller, not written to disk), compact:
- `projects`: per project `{id, paths, include, exclude}` suggestions (`paths` are working code roots, never `.` unless sources sit at the root; `include`/`exclude` globs).
- `conventions`: up to 10 candidate rules, each `{rule, quote, location, basis}`: `quote` is 20+ characters copied verbatim from `location` (`path:line`), `basis` is `written` when a project document states it or `inferred` when you saw it in code. A candidate is not repeated in `conventions.md`, which keeps only descriptive facts.
- `context files`: files written, plus any remaining `check.problems`.
- `unknowns`: anything unclear worth asking the user (optional).
