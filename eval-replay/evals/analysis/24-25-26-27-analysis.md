# AMBICODE v7: audit of eval runs 24–27

Date: 2026-10-07. Scope: the saved runs in `eval-replay/evals/24-25-26-27`, their matched bare reference, v7 architecture, current implementation, and the eval tooling. This is an analysis and proposed improvement sequence, not an accepted implementation plan. No paid runs, diagnostics, builds, reviews, or product-source changes were performed.

The plugin improves average localization recall against the cached bare reference, but the evidence does not yet establish a stable, broadly reliable investigation workflow. The strongest reproducible problem is the search map delivered to the model: it contains **no historical truth file in four of six cases**, and its average visible recall is **13.1%**. The model often recovers through its own searches. A second major problem is the ruler: a saturated grader and a shared, newer repository snapshot can reward or penalize answers differently from the historical file oracle. Fix those measurement problems before tuning the model to reproduce the oracle.

The v7 direction is sound: trusted hooks start the route, code performs grounding, the model receives one investigation step, and Stop saves the answer and closes the route. Keep that division. Improve the delivered search evidence and file-reading efficiency inside it. The results do not justify adding a larger agent framework or making a language server the first intervention.

Your three notices translate into specific changes:

1. Make eval gate answers deterministic and accept the required workflow decisions through trusted eval inputs; skip optional task review. There are **zero AskUserQuestion calls in these four runs**, so this is a concrete future-suite fix, not the explanation for their measured failures. The existing task transport explicitly opts into optional review.
2. Organize reads into bounded dependency waves. Batching already happens, but run 27 still has **51 single-file read requests out of 112 inferred read requests**. Avoidable serial search and rereads remain visible in individual traces.
3. Continue using the cached bare baseline. **All four runs already reuse run 22.** Pin its identity and compatibility centrally; do not rerun bare for each iteration or compare against whichever report happens to be newest.

One small but real acceptance failure also needs to be recorded: replaying the repository's existing gate gives run 27 a cost ratio of **1.100848751×**, including judging, against a **1.1×** limit. It fails that gate. Model-only cost is 1.088532×, and two-decimal formatting prints both the failure and the limit as 1.10; neither is a reason to silently pass it.

### The exact gate and the reports disagree in important ways

## The eval ruler needs repair before optimization

### Perfect pass does not mean complete localization

All 108 plugin attempts pass the host graders, while run 27's file recall is 64.0%. The generated LLM grader requires **at least one historical truth file**, with weight three; six other binary checks bring the total weight to nine. It does not measure complete file coverage or punish speculative file lists adequately. This is why the aggregate pass score saturates while useful localization measures remain mediocre.

Ownership: [bench-cases.mjs](../../evals/scripts/src/cases/bench-cases.mjs), `graderFiles`, lines 178–198 onward. Keep the safety/behavior checks, but report deterministic normalized precision, recall, F1, essential-file coverage, unsupported assumptions, and citation/read grounding independently. Do not call a 100% pass score “100% localization.” Avoid adding another paid judge for a metric that can be calculated from saved paths.

The original combined report also uses an exact-path proxy. In `26 / fe-vs-438 / rep 2 / e-Ez78YY`, valid paths omit the `main/` prefix. The exact proxy scores recall zero; the repository's normalized scorer scores **13/14 = 92.86%**. Correcting this one answer raises run 26's mean recall from **64.75% to 67.33%**. Preserve the original report as historical output, but use one scorer consistently for decisions.

There is a subtler normalization risk: `namedFiles` resolves unique suffixes against truth, rather than the entire repository catalog. A suffix may be unique in truth but ambiguous in the repository. Future normalization should use the frozen catalog, not oracle-assisted resolution. Ownership: [bench-score.mjs](../../evals/scripts/src/analysis/bench-score.mjs), lines 31–54. Version that change; do not silently replace old scores.

### Shared snapshots and historical truth are not the same problem

The localization prompt says the ticket is “about to be implemented.” Its scaffold copies the shared project's current `src/` or `main/` and makes a single snapshot commit. Truth comes from a historical merged change, filtered to files that still exist. There is no case-specific base commit in the saved localization truth metadata.

Ownership: [bench-cases.mjs](../../evals/scripts/src/cases/bench-cases.mjs), `promptFile` at line 135, `scaffoldFile` at line 154, and truth filtering near line 494. Existing safer machinery already exists in [base-scaffold.mjs](../../evals/scripts/src/cases/base-scaffold.mjs), `baseOf` and `baseScaffoldScript`.

This mismatch is visible in answers and read source:

- `27 / be-vs-5903 / rep 5 / e-ypRse4`: the organization consent flag and validation/controller plumbing already exist. The answer identifies that implemented state, then proposes missing downstream report/upload changes. Its final file list can have zero historical matches while earlier prose mentions truth files and the host grader passes it. The ticket, current tree, historical oracle, final-section scorer, and grader are measuring different things.
- `26 / fe-vs-438 / rep 2 / e-Ez78YY`: employee creation/prefill functionality already exists. The answer emphasizes remaining locale/template changes. Omitting an already-implemented historical dialog file is not automatically a reasoning failure.
- `27 / be-vs-5075 / rep 5 / e-aCDRkO`: the GEADV analytics endpoint/projection already exists; other historical middleware/error targets are harder to derive from the ticket alone. Some model additions are assumptions, while some historical changed files may be incidental maintenance rather than necessary touch targets.

A merged file set is useful evidence, but it is not automatically the minimal required change set. Audit truth into essential, supporting, incidental, and already-implemented roles. Do not reward a model for reproducing unrelated merge maintenance or train it to pretend existing behavior is absent.

For a future dataset version, scaffold each ticket at its actual pre-change base and include manifests/configuration needed for accurate project discovery. Use the existing archive builder; withhold future commits and saved conclusions. Capture tree/config/truth/prompt/grader hashes. If co-change is tested, provide only history at or before that base, or a pinned derived history artifact. Do not hand the model the future merge history.

Changing the scaffold or oracle invalidates the old reference for that new dataset. Preserve this historical dataset and run 22 for historical comparisons. A separately versioned, repaired dataset may need a baseline once; that does not imply rerunning bare for every plugin revision.

### Two truncation stages hide ranked evidence

## Reads and turns: address your second notice precisely

The route already says “Read batched: several files per call, then the spans that matter.” The harness does not force one read per turn. It controls route steps, not the model's individual Read/Grep/Bash planning. Ownership: [read.md](../../routes/investigate/read.md), line 3; [investigate.yaml](../../routes/investigate/investigate.yaml), the single read model step.

Grouping explicit read operands by parent model message gives:

| Inferred reading metric | Bare 22 | 24 | 25 | 26 | 27 |
|---|---:|---:|---:|---:|---:|
| Read requests | 47 | 60 | 43 | 116 | 112 |
| Single-file requests | 24 | 28 | 24 | 51 | 51 |
| Batched requests | 23 | 32 | 19 | 65 | 61 |
| Attempts with at least one batch | 15/18 | 18/18 | 14/18 | 35/36 | 33/36 |
| Paths per read request | 1.79 | 1.80 | 1.65 | 1.80 | 1.88 |

Batching is therefore partially working. The remaining question is which singleton requests are necessary because new evidence reveals the next dependency, versus avoidable because the paths are already known. Do not set a blanket “zero singleton reads” goal.

`27 / be-vs-5075 / rep 5 / e-aCDRkO` illustrates the avoidable part: 19 harness turns, 18 tools, repeated probes across controller/model/helper paths, six direct Read calls, and overlapping AnalyticsController reads around offsets 425 and 500. Several searches over independently known locations could be one request. `27 / fe-vs-6269 / rep 6 / e-u8Wcra` takes a wrong subject-form detour before finding NOM; one later mixed Bash result is 11,454 bytes, combining multiple spans and grep results. Batching without selection/size discipline can still inflate context.

Use a two-part reading policy inside the existing step:

1. One discovery wave establishes a bounded set of likely owners and paired files from map, imports, exact identifiers, and request roles.
2. Read the independently known files/spans together, then decide whether a specific new dependency requires another wave. Reuse already received spans; request only missing ranges.

A practical optional helper is a code-owned `read-many` capability with a shared repository root, path validation, requested anchors/ranges, aggregate byte budget, per-file truncation, and hash/line receipts. A normal wave might contain 3–8 relevant files; that is a proposed experiment, not a hard universal rule. Existing parallel Read calls or a bounded Bash batch can also implement the policy without a new framework. Preserve model judgment about which evidence is needed, and never dump the entire top 20 by default.

Measure dependency waves, model requests, repeated-span bytes, relevant-file coverage, and resulting precision/recall together. Fewer tool calls alone is not success if the one call returns 50 KB of irrelevant source.

### Turn definitions must stay separate

There are at least four different counts:

- Host/harness turns, which in these traces approximately follow tool calls plus the final answer.
- Actual model/API requests; multiple tools may be emitted in one model message.
- Harness model-step deliveries: all typed investigations use one of six allowed steps.
- Ledger `turn` summaries emitted by Stop, which can summarize multiple host requests.

Thus 19 host turns with one model-step delivery is not evidence that the six-step budget failed. v7 removed `toolTurns`; the engine does not currently cap arbitrary within-step host calls. If a read/request budget is wanted, name and instrument it explicitly, decide which layer can actually enforce it, and keep it distinct from route-step limits. First improve targeting; do not truncate a legitimate investigation solely to hide its tail.

## Context, caching, and cost attribution

Typed investigations add about **2,303–2,312 tokens to the first context**, roughly 14.2% over bare. Untyped installation adds about **711 tokens**, 4.4%. The ledger-delivered payload estimate averages roughly 543 tokens by bytes/4; it is only part of the overhead. Contract, skill metadata, instructions, hook rendering, and host framing contribute too. A ledger-payload estimate is not an end-to-end context measurement.

What already works: [common.ts](../../src/skills/common.ts), lines 110–121, suppresses an envelope and AC payload when the source is merely the user's existing argument text. Policy pointer-only payloads are also suppressed for this route. The launch does not require a separate model Skill invocation or legacy prepare ceremony. These are useful reductions; retain them.

The peak is dominated increasingly by subsequent source/results, not only the initial injection. Run 27's average peak grows to 34,376 and p95 to 50,095. Tool-result means are near bare again by run 27, and output is about 25% higher. Improve wrong-neighborhood detours, overlapping reads, and speculative answer lists before trimming a few words from the route.

Caching complicates the cost story. Mean cache-created inputs are 25,560 / 26,361 / 26,369 / 26,101 / 27,682 tokens for 22 / 24 / 25 / 26 / 27; cache-read inputs are 177,404 / 171,713 / 182,958 / 172,444 / 177,612. Summing cached tokens across API requests is repeated traffic, not one context window. Fresh uncached input is only about 15–16 tokens per attempt under these host metrics. Report window size, repeated cached traffic, output, and billed dollars separately; a lower summed input count need not imply a lower bill.

Observed hook-time totals average about 533 / 374 / 491 / 623 ms for 24 / 25 / 26 / 27. They are partial instrumentation, not the complete grounding/launch latency. Policy omitted-rule counts similarly describe selection, not saved tokens from every policy source. Do not infer causal savings from either counter alone.

The untyped contract overhead is measurable even without a route. Deferring parts of that contract until explicit activation is a possible separate experiment, but it changes the instruction architecture. It is lower priority than delivered-map correctness and should not be mixed into a search tuning comparison.

### Stop catches a real citation problem, with limited scope

### Evidence is incomplete even when the user gets an answer

The harvester preserves traces, sessions, and ledger copies, but not all referenced notes and step/config artifacts. Consequently it cannot fully verify that final evidence bodies match ledger hashes. Successful session stderr is helpful, not a substitute for those artifacts.

The automatic navigation line filters CLI `search` entries, while grounding records `map` entries. All these ledgers have zero explicit CLI search events, so saved navigation can say no CLI search was recorded even though code-generated maps and model reads happened. This is narrowly accurate but a poor end-to-end investigation receipt. Ownership: [navigation-line.ts](../../src/modules/evidence/report/navigation-line.ts), line 4, and `saveAsNote` in Stop. Include map provenance and bounded read receipts under their actual origins; do not pretend model grep commands were harness CLI searches.

### Read/error instrumentation has blind spots

Most source reading happens in Bash. Counting only direct Read tools severely understates reading. A mixed Bash command may contain grep and multiple sed/cat operations; `callClass` assigns one class, prioritizing search, while `READ_CLASSES` only accepts Read/cat. Real reads in mixed commands disappear from the standard report. Truth-assisted path extraction also does not reliably resolve shell cwd, globs, or failed conditions.

Ownership: [layer-audit.mjs](../../evals/scripts/src/analysis/layer-audit.mjs), `callClass` at line 35; [run-report.mjs](../../evals/scripts/src/analysis/run-report.mjs), `toolFiles` at line 83 and `READ_CLASSES` at line 88. Represent a tool call as multiple operations, or log actual reader receipts. Avoid forcing one mutually exclusive search/read label onto compound shell commands.

The one-off report's path-error regex is also a signal rather than a reliable error count: source text containing “not found” can match it. Confirmed tool errors are 2 / 3 / 5 / 5 / 7 for 22 / 24 / 25 / 26 / 27; broader path-error signals are 7 / 5 / 13 / 16 / 13. Do not equate those series. Some actual errors involve repeating `cd repo` after cwd already changed or unquoted `--include=*.ts` under zsh. Use an explicit root/cwd contract and quote glob operands; classify failures from tool status/stderr, not arbitrary source phrases.

## Eval gate policy: your first notice

No matched attempt calls AskUserQuestion. The 90 routed runs have no gate-answer or preanswer records because the investigation map is nonempty and requirements are local. Therefore accepting questions would not alter this dataset's observed trajectory.

There is nevertheless a concrete contradiction for task evals: [prompt-transport.mjs](../../evals/scripts/src/harness/prompt-transport.mjs), line 16, defines `/ambicode:task --headless --answer review-offer=run`. Your policy requires **skipping that optional review offer**. Change the task-eval command to the semantic skip choice. The dedicated review command's `estimate=run` should remain, because review is the requested work in that suite. Required implementation checks and plan checks likewise remain required; “skip extra tools” must not silently turn verification off.

The current engine deliberately distinguishes trusted hook/user preanswers from model-supplied CLI answers. Ownership: [prompt-launch.ts](../../src/hook/events/prompt-launch.ts), flag parsing and hook-channel launch; [engine.ts](../../src/harness/engine/engine.ts), trusted preanswers; [answers.ts](../../src/harness/gates/answers.ts), `serviceGate`, `recordFlagAnswer`, headless defaults; [consent.ts](../../src/harness/gates/consent.ts); and [gate-answer.ts](../../src/hook/events/gate-answer.ts), exact question/gate binding.

Implement an **eval-side decision policy**, not a production-wide Accept default:

- Accept plan/config/rule/application decisions with their correct gate labels and object hashes. Some routes say Apply or implement-anyway rather than Accept; map semantics, not one literal string.
- Bind acting choices through the trusted launch/host channel. Do not let the model manufacture user consent with `--answer` or a narrative claim.
- Skip optional post-task review. Continue required workflow steps and the core tool of a dedicated review/check suite.
- Supply case-specific selector answers where needed. A scope question requires an actual term; Accept is not a usable answer.
- Bound budget-continuation choices so an eval cannot accept an infinite loop. Unexpected questions should produce a visible coverage gap, not an invented answer.

Keep production headless defaults nonacting. Add focused checks when implementing: task prompt chooses skip; plan acceptance binds the current draft; required check consent is present; dedicated review runs; unknown gate/selector is reported. The zero AskUser observations here are not proof that the whole gate system is covered.

## Recommended sequence and ownership

### P0: make the next comparison trustworthy, without model spend

1. **Unify score, verdict, and provenance.** Use one normalized scorer and baseline resolver; include judging in the declared gate cost; print sufficient precision; expose measurement gaps; separate observation thresholds from acceptance rules. Bind bundle, tree, config/profile, prompt, truth, grader, host, and scorer hashes. Owners: eval `bench-score`, `eval-gate`, `run-report`, prompt/run transport.
2. **Fix final-artifact capture.** Completion acknowledgment/export must happen before sandbox teardown. Preserve terminal ledger, note body, delivered map, and manifests; validate references/hashes and distinguish explicit from inferred closure. Owners: `evals-bench`, `trace-analysis`, hook/Stop evidence export.
3. **Apply your eval policy.** Skip optional task review, provide trusted semantic acceptance answers for required gates, leave naked prompt/reference bytes intact. Owners: `prompt-transport`, eval case metadata/host gate adapter. Do not change production consent defaults.
4. **Audit the six case premises and truth roles.** Record already-present behavior and incidental merged targets. Prepare a separately versioned pre-change dataset using `base-scaffold`; preserve all old artifacts and cached baseline. Owners: localization generation, truth/schema/manifest tooling.

Validation here is offline: reproduce all existing scores and gate decisions, deliberately reject incompatible reference manifests, verify final exports against hashes, and inspect gate bindings with deterministic fixtures. No fresh bare eval is necessary for those fixes.

### P1: improve useful grounding before adding tools

5. **Repair the delivered-map contract.** Separate original ranking, retained full map, and model-visible paths. Reserve path/anchor coverage; shorten provenance headers; avoid two unrelated truncations governing the useful subset. Owners: `search/text/map.ts`, skill map handler, map-analysis/report tooling.
6. **Run model-free search ablations on frozen cases.** Compare pass 1 alone, current two-pass, constrained/diverse pass 2, exact-identifier retention, request-aware companions/catalog lookup, and measured profiles. Report ranked and delivered recall, precision/useful-family coverage, zero-useful-lead rate, bytes, and latency. Do not select changes using the oracle at runtime.
7. **Fix shortlist frequency/caching behavior.** Preserve saturation/full-frequency information before specificity scoring; reuse request-local catalog/grep/history data across passes; measure process counts and wall time. Owners: `locate.ts`, git port/adapter, map request lifecycle. Preserve determinism and snapshot invalidation.

Suggested experimental targets, not existing acceptance rules: reduce visible zero-truth cases from four to zero on this frozen diagnostic set; move delivered macro recall toward at least 60% without speculative-family inflation; reduce median/p95 grounding latency under equal inputs. Historical truth ambiguity means these targets must be accompanied by manual role/premise checks. The older map-recall target on a different ten-case/53-file dataset must not be treated as an achieved target on these six cases/38 files.

### P2: make evidence consumption efficient

8. **Add bounded read planning.** One discovery wave followed by a batch of known spans, with new waves only for concrete dependencies. Prototype using existing tools before deciding whether a `read-many` module is worth its API surface. Owners: investigation payload/instruction and, if justified, a reader module with evidence receipts.
9. **Fix compound-operation reporting.** Count reads within mixed Bash, model requests separately from tools, repeated spans separately from new files, and shell failures from actual status. Owners: `layer-audit`, `run-report`, trace extraction; optional read receipts make these less heuristic.
10. **Tighten answer roles.** Required files, conditional files with a stated assumption, and background read evidence should not be one undifferentiated list. Protect the high precision of REBA/user-table while improving the weak NOM and organization cases. Owners: `routes/investigate/read.md`, answer parser/scoring schema.

Success means fewer avoidable requests and reread bytes at equal or better quality. In particular, investigate the NOM case's 1.54× cost and low precision, and the analytics case's 19-turn chain. Do not optimize average turns while preserving the same wrong search detours.

### P3: validate the plugin direction with targeted future runs

Once free checks and offline search experiments select a concrete candidate, run only the plugin arm against the pinned compatible baseline. Change one coherent control surface at a time; do not mix map ranking, shared instructions, grader/scaffold repair, and host/model upgrades in one causal claim. Keep the same prompt treatment when comparing plugin revisions.

Report case-level precision/recall/F1, uncertainty using case-blocked resampling or another declared method, run variance, cost including judging, p95 latency/context, useful delivered-map coverage, and artifact completeness. Use a fixed baseline tolerance and a predeclared meaningful improvement target; treat high variance as its own problem. Six cases are diagnostic, so expand ticket/task diversity separately rather than buying many more repetitions of the same inputs.

Add targeted coverage for currently absent behavior: required/optional gates, task checks and interrupted verification, plan acceptance, review quality/cost, configuration/profile generation, MCP capture, compaction/resume, and crash/terminal export. Those suites should reuse their own compatible baselines, with optional post-task review skipped as requested. Those future runs are not necessary to produce this report.

## What to keep, and what the evidence cannot yet settle

Keep trusted typed activation, code-owned grounding, one compact investigation model step, args/AC deduplication, deterministic replayable search, cached references, and Stop's bounded correction/save behavior. REBA and the user-table answers show that the workflow can produce strong, precise results without extra agent ceremony.

Change the delivered evidence and the measuring pipeline first. Then improve feature ownership/ranking, profile-backed related files, and bounded reading. Optional indexing or deeper dependency tooling should earn its place in offline ablations. A bigger context budget, more forced reads, an always-on reviewer, or more elaborate routes would add cost before addressing the demonstrated failures.

The unresolved questions are specific: which exact bundle ran each attempt; whether every missing copied tail existed before teardown in 24/26; how much improvement remains after correcting case premises; which independent singleton reads can be removed without losing evidence; and whether profile/index changes help beyond a repaired text map. Bundle manifests, terminal exports, corrected case bases, read receipts, and frozen-input ablations would resolve those uncertainties. The current 100% plugin pass score does not.
