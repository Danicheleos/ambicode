  command straight away and recorded no check.

The `fix-the-cause` rule did not hurt plan quality. Criterion 2 ("extend existing code, no parallel
modules") passed in 5/5 of the re-judged plans.

## 2. plan-accept: the judge's criterion 3

`plan-quality` is an LLM judge with three votes and this grader text:

```
- Every iteration has Goal, Changes, Tests, Accept, Checks and Leaves out (or plainly equivalent headings).
- Changes extend the existing Invoice interface …, service.ts and invoicesRoute … rather than new parallel modules …
- Tests say what fails first, before the change.
```

The harness keeps only the votes, not the judge's reasons:

| run | votes |
|---|---|
| 1 | FAIL PASS FAIL |
| 2 | FAIL ×3 |
| 3 | FAIL ×3 |
| 4 | FAIL ×3 |
| 5 | PASS |

To get the reasons, I re-ran the criteria once per plan body with `claude -p --model sonnet`, asking
for a verdict per criterion. That cost a few cents.

```
run  c1 headings  c2 extend existing  c3 fails first   verdict
1    PASS         PASS                FAIL             FAIL   "covers one test per iteration rather than the Tests as a whole"
2    PASS         PASS                PASS             PASS   (harness judges: FAIL ×3)
3    PASS         PASS                FAIL             FAIL   iteration 2: "nothing behavioural to test"
4    PASS         PASS                FAIL             FAIL   iteration 1 test has no fail-first line
5    PASS         PASS                FAIL             FAIL   (harness judges: PASS) iteration 1 route test has no fail-first line
```

What this shows:

- **Criterion 3 is the only one that fails, and it is ambiguous.** Each plan states one fail-first
  condition per iteration. The judge sometimes reads the criterion as "every test", and its verdict
  flips between runs on the same body: run 2 failed 3/3 in the harness and passed here, and run 5
  did the opposite.
- **The instruction asks for less than the judge checks.** `routes/plan/write.md:7` asks for
  "*Tests*: what it adds or changes, and what fails first, before the fix". That is one fail-first
  line per iteration, and the plans follow it.
- **Criterion 2 is unaffected by the new rule.** 5/5 plans add `createInvoice` inside the existing
  `src/invoices/service.ts`. Run 5 explicitly cites a reuse sweep that found 0 existing creators.
- **The `no-checks-run` miss is a grader false positive.** The grader matches
  `jest|eslint|npm (test|run)` in any Bash input. Run 3 wrote the plan body with
  `cat > … <<'EOF'`, and that body contains "*Checks*: jest …, eslint on `src/invoices`". The model
  ran no checks.

Why it passed 3/3 before: those were single runs. A judge that fails about 4 in 5 on this ambiguity
can still pass three single runs in a row. I can't tell drift from luck without the earlier plan
bodies, and they were not kept.

## 3. review-regression: tests are second in the run step

`routes/review/run.md`, in full:

```
Run the review command from the payload below, unchanged. It pins the change, … and prints the report.
Tests are yours to choose. Before the command, run the ones that cover the change and record each with
`{cli} check --task {task} --name <check> --file <file> … --phase green`. A review with no recorded check
reports that as a gap, not a pass.
```

Main-session actions per run:

| run | actions | outcome |
|---|---|---|
| 1, 2, 4, 5 | `review --task rev-math` → Agent (reviewer) → `review record` | no check recorded |
| 3 | `ls`, `git diff`, then jest on `tests/math.test.js`, which fails; `check --help`; `check --name jest` and `check --name unit`; then `review` → Agent → `review record` | 2 check entries; a `limit review-run` entry and two `repeated` steps |

At effort low, the first sentence decides what the model does, and the tests come second. The
review is still recorded as `partial` with the gap reported, so the output is honest; it just
doesn't run the test.

Run 3 has a second issue. It recorded the failing jest run with `--phase green`. Whether `check`
records the actual exit status, or trusts the phase it is given, is not checked here.
